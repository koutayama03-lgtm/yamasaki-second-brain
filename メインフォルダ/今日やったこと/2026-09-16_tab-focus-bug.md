# Tabキーフォーカス遷移バグの調査 & XML/propertiesの理解

## 今日のタスク
- 業務：キーボードのTabキー押下時、フォーカス遷移がおかしくなる不具合の原因調査
- 使用技術：XML、JavaScript（Java案件、既存の伝統的アプリケーション）
- トレーナーからの指示：「XMLの情報から呼び出し階層を辿れ」

## 調査の進め方（整理したメモ）

### 原因として疑うべき3パターン
1. **XML側のtabindex属性の設定ミス**
   - `grep -rn "tabindex" --include="*.xml" .` で検索
   - 数値指定のtabindexが散らばっていて順序が壊れているケースが多い
2. **JavaScript側でのフォーカス制御・キーイベントの横取り**
   - `keydown`/`keyup`で`keyCode == 9`（Tab）を判定し、`preventDefault()`と`.focus()`で独自に遷移を上書きしているパターン
3. **DOM構造と見た目の表示順序のズレ**
   - CSSの`float`/`position: absolute`/`flex`の`order`などで見た目とDOM順序がズレている
   - Tab遷移は基本的にDOM上の記述順で決まる

### 実際に取った手順
1. Chromeデベロッパーツールで該当ボタンのidを特定
2. IntelliJの「Find in Path」（Ctrl+Shift+F）でプロジェクト全体を検索
   - 検索対象をJavaファイルだけでなく `*.java, *.jsp, *.js, *.xml, *.properties` に広げる
3. ヒットしたファイルを拡張子で仕分け
   - `.xml` → 画面部品の定義本体
   - `.js` → イベント処理・DOM操作（Tab不具合の本命）
   - `.java` → 対応する処理クラス
4. 「呼び出し階層」は、JS側のイベントハンドラから逆向きに辿るのが早い
   - JS側のTab処理・フォーカス処理を先に特定 → そこで使われているIDを確認 → XMLの定義へ → そのXMLを読み込むJavaクラスへ、という順で遡る
5. IntelliJでXML属性を右クリック→「Find Usages」、または属性左のガターアイコンでフレームワーク連携ジャンプができないか確認

## XMLについての理解の整理

- XMLは「データの構造をタグで表現するマークアップ言語」。HTMLと違い、画面表示ではなく**データの構造化・受け渡し**が目的
- タグ名は自由に定義できる（自己記述的）
- Mavenの`pom.xml`やSpring設定など、Java界隈では今でも現役
- **誤解していた点**：XMLは「JavaとJavaScriptの橋渡し」ではない
  - 正しくは、XMLは**両者が独立して読みに行く共通の設定データ置き場**（＝共有される台本・住所録）
  - JavaとJavaScriptが直接やり取りしているわけではなく、それぞれ別々に同じXMLの同じIDを参照しているだけ

## propertiesファイルについての理解の整理

- `hogehoge=hogehoge` のような `key=value` 形式は、XMLではなく**プロパティファイル（.properties）**
- 目的：**プログラムのコードを変更せずに、設定だけを外部から差し替えられるようにするため**
  - 例：文言修正のたびにJavaのソースを書き換えてコンパイルし直す必要がなくなる
- 主な用途
  - 多言語対応（i18n）：言語ごとにpropertiesファイルを分けて、同じkeyで文言だけ切り替える
  - 環境ごとの設定切り替え（開発/本番でURLを変える等）
  - 画面部品のIDと文言・設定のマッピング
- 左側（key）＝値を検索するための識別子（Javaのメソッドに文字列として渡されることが多いが、「引数」そのものではない）
- 右側（value）＝ただの文字列。**プロパティファイルの値は基本的にすべて文字列として扱われる**
  - 数値として使いたい場合はコード側で変換が必要
- key と value が同じ文字列になっているケース
  - 多言語対応の基準（フォールバック）ファイルとして意図的に揃えている場合
  - 開発中の仮置き・テストデータの場合
  - → 実物を見て、どちらかを周囲に確認する必要あり

## valueOf()メソッドとの繋がり

- propertiesファイルやXMLから読み込んだ値は、まず「文字列」としてやってくる
- プログラム内では数値・真偽値・enumなど本来の型として扱いたいことが多い
- その「文字列→本来の型」への変換を担うのが `valueOf()`
  - `Integer.valueOf("123")` → 数値変換
  - `Status.valueOf("ACTIVE")` → enum変換（key=valueが同じ文字列になっているケースとも関連しそう）
