山﨑君、1章を読み切ったわ。「抜けなく」と指定するのだから、長さは覚悟なさい。それにしても、新卒になってようやく基礎を勉強し直すなんて、順番が逆じゃないかしら。まあ、始めないよりはましだけれど。

## 結論

1章の主張はこの一文に尽きるわ。**「プログラマからエンジニアになるには、コードを書く力だけでなく、ソフトウェア開発ライフサイクル（SDLC）全体の基礎スキルと、学び続ける姿勢が必要」**ということ。

## 1章の内容（節ごと）

### 導入（p.1）
- ソフトウェアエンジニアには、顧客のニーズの理解、保守しやすいコード、テスト、UI、アーキテクチャ設計、データの扱い、本番デプロイなど、幅広いスキルが必要とされる。
- コードだけ書いていてはいけず、ソフトウェアエンジニアリング全体を理解しなければならない。
- そのために、SDLC全体の基礎スキルに加えて、効率的に働くこと、わからないことを素直に認めること、学び続けることが求められる。
- 本章の目的は、筆者たちが苦労して得た教訓を伝え、道のりを円滑にすること。

### 1.1 ソフトウェアエンジニアとは（p.1〜2）
用語は曖昧で、次のように整理されている。
- **プログラマ／コーダー**
  - コードを書くタスクだけを担う人を指すことが多い。
  - 特定の言語やフレームワークには精通していても、SDLC全体は理解していないこともある。
  - バグ修正や機能実装だけでは昇進が難しい。
  - 脚注には、このような技術者はエージェント型コーディングシステムに置き換えられるおそれが高い、とある。
- **開発者**
  - ソフトウェア提供の全体像をより深く理解している。
  - 複数の言語・フレームワーク、さまざまなビジネス領域を経験している。
  - SDLCのより多くの段階を経験し、後輩のメンターやペアプロの相手を務めることもある。
- **ソフトウェアエンジニア**
  - SDLC全体にエンジニアリングの原則を適用する。
  - コードが書けるのは当然の前提で、スケーラビリティ、信頼性、効率性、セキュリティも検討する。
  - アルゴリズムや設計を深く理解している。
  - ルールを知るだけでなく、曲げるべき場合、破らなければならない場合も把握している。
  - 稼働中のシステムの中でも、非常に複雑で重要なものを担当する。
- ブートキャンプや大学は、通常コードを書く技術面を重視し、開発者やプログラマを生み出す。これはキャリアの出発点にすぎず、昇進や面白いプロジェクトのためにはそれだけでは足りない。

### 1.2 基本が重要（p.2〜3）
- プロスポーツ選手は、ハイライトに出るようなプレーよりも、始めた頃に学んだ基本に大半の時間を費やす（ゴルファーならスタンス・グリップ・アライメント、バスケ選手ならレイアップ・パス・フリースロー）。
- 基本は面白くなくても、それがなければ高いレベルには到達できない。
- キャリアの大半は既存コードと向き合うことになる。他人のコードを読み、初めて触れるコードベースを素早く理解することが成功に不可欠。
  - 見慣れないコードベースに恐れを抱いてもよいが、よくわからないものに向き合うことに慣れる必要がある。
  - 数か月経っても細部まで理解できないことがあり、変更の前にすべてを理解する必要はない。
- 後任者の負担を軽くするコードの書き方は、まだ詳しくないかもしれない。
- テクノロジーは止まらないので、新しいことを学ぶ能力が必須。
- 多くのプログラマは新技術や言語の新機能ばかり追い、昇進につながる普遍的なソフトスキルを軽視しがち。基本は流行ほど話題にならないが、できていれば広い範囲と責任を伴う機会を得られる。

### 1.3 ソフトウェアエンジニアになるためのさまざまな方法（p.3〜4）
- 道は、CS学位、ブートキャンプ、独学、関連分野（電気工学など）の学位からの転向などさまざまで、**どう学んだかはあまり重要ではない**。
- 独学
  - 授業料がかからず、適性によっては数年ではなく数週間で習得できる。動画やチュートリアルも豊富。
  - 一方で、情報探しが大変で、厳しい自己管理が要る。教材の品質にばらつきがあり、試行錯誤も多い。
- 学部のCS課程
  - 大学院進学の準備として設計されており、アルゴリズム、言語設計、コンパイラ理論、OSなどに重点がある。
  - 日々のアプリ開発の準備とは限らない。プロジェクトは小規模で数か月以内、既存アプリに縛られないゼロからの開発がほとんど。
- ブートキャンプ
  - 特定の知識を短期間（多くは数週間）で集中的に学び、流行の言語・フレームワークに重点を置く。実践的だが、人気は浮き沈みするので知識が長く役立つとは限らない。
  - 大学内に設置されたり、学部のCS講座の教員が教えたりすることもあり、教える側にはあまり違いがないかもしれない、とも書かれている。
- 必要な時間の目安
  - ブートキャンプは数週間で約600時間で、指導者にほぼ常時対応してもらえる。
  - 準学士号は1〜2年で850時間。
  - 学士号は4〜5年で約1,400時間。
- 学部卒は最初のうちは有利と言われるが、時間が経つと差は埋まっていく傾向がある。
- 数学を必須とする見方に対しては「実際にはそんなことはない」と明言されている。
  - コーディングはコミュニケーションであり、仕事の大半はコンピュータではなく他の開発者とのやり取り。
  - 言語能力は数学的スキルよりはるかに重要で、コードを書くことは数字ではなく言語を使うこと（2章で説明）。
- 成功に必要なのは、問題解決能力、探究心、創造性。そのマインドセットが重要で、学び方を言い訳する必要はない。

### 1.4 教えられたことと知るべきことの違い（p.4〜5）
- 多くの人は言語を1〜2つ学び、foo や bar といった汎用的な変数名を知り、デバッグや効率的なアルゴリズム設計も少しは学ぶ。
- 重要なことの多くは一般的なカリキュラムや独学では学べない。時間不足か、すでに知られていると想定されているため。
  - 例：他者との協働、コードの読み方、可読性の高いコードの書き方、レガシーコードの扱い方（脚注では、デバッガーやモダンエディタの使い方なども挙げられている）。
- 教育では、技術的負債のない白紙のグリーンフィールドプロジェクトを学ぶことが多い。時間的制約から、スキル練習や概念理解のためにゼロから始める。小規模で単独動作のものが多く、一人でコーディングすることも多い。教育環境では有効でも、実際の業務を反映していない。
- 実際の現場
  - ほとんどの時間は、既存のレガシーアプリや、関わる前に下された決定による負の遺産のあるプロジェクトと向き合う（脚注：なぜそうなっているのかを問うのは意味があるが、同僚の推測も自分と同じくらい当てずっぽうかもしれない）。
  - 新しいコードベースでも、数か月で技術的負債は溜まる。
  - 現代のプロジェクトでは、世界中のチームが数百万行のコードを扱い、常に誰か（チームメンバーや顧客）と協働する。
  - コードは本番環境で稼働し、人々の信頼のもとでビジネス価値を生む。
- プロジェクトは決して終わらない。コードは生涯の大半を**保守フェーズ**で過ごす。ソフトウェアは明確な開始と終了を持つプロジェクトではなく、**継続的な投資が必要なプロダクト群**であり、ビジネス価値を提供する限り投資は続く。

### 1.5 怠惰なプログラマの精神を身につける（p.5〜6）
- 「怠惰」とは、サボることではなく**効率性に焦点を当てた哲学**。
- 新人は本能的に急いで解決策を探し、十分に考えず書き始める。戦略的に怠惰になって考える時間を持てば、生産性が上がり、より良い解決策が見つかる。
  - 引用：「時間をかけることで、かえって時間を節約できる」（Pat Parelli によるとされる）。
- 力任せのアプローチは、そこから始めてもよいが、何度も設計を見直すべき。
- ビッグオー記法のような概念の理解は有益（脚注：あるアルゴリズムが他より効率的であることを説明するもの）。バブルソートが最も効率的ではないと学んでいるはずで、最良・最悪・平均ケースを考慮して選ぶべき。
- 特定の問題を解くのは自分が初めてではない場合が多い。既存の解決策やライブラリを探すこと。10分の検索が数日分の作業を節約することが多く、「もっと簡単な方法がある」と感じたらおそらく存在する（3.1「車輪の再発明は避ける」で詳説）。
- **コラム「大文字化という作業」（Nate の体験）**
  - 請求先住所を大文字化する単純なタスクを任された。
  - 指定された社内関数は引数が10個以上もあり、理解に何時間もかかりそうだった。
  - 検索すると、言語に組み込みの大文字化関数があったので、それを使った。
  - 翌週のミーティングで同僚に「Joe の関数を使ったのですか？」と聞かれ、使っていないと答えると全員が振り向いた。
  - 最も経験の浅い自分以外、誰も組み込み関数の存在を知らなかった（関数が書かれた後に言語機能が追加された可能性があるが、詳細は不明）。
  - 教訓は、もっと簡単な方法があると思うなら時間をかけて探すこと。数時間の調査で数日〜数週間を節約できるかもしれない。

### 1.6 新たな視点の価値（p.6〜7）
- 引用：「最も危険な言葉は『我々は常にこの方法でやってきた』です」（Grace Hopper）。
- 新人は経験年数やコード量で劣っても、**新たな視点**という貴重な資質を持つ。
  - 過去の決定事項や、もはや有用でない慣習に縛られていない。
  - 革新的な解決策を生み、非効率を指摘し、長年の前提に疑問を投げかけられる。
  - 停滞気味のプロジェクトやチームに活気を与えることもある。
- **コラム「昔からそうしてきたから」（Nate の体験）**
  - クライアントのアプリで、夜間バッチ（ウィジェット処理）が一晩で終わらなくなっていた。会社の成長で顧客とウィジェットが増えたため。
  - アーキテクチャを検証し、「ウィジェットAの処理はBと関係あるか？」と尋ねると、最終の集計以外は独立していた。
  - そこで、ワーカーを立ち上げて並列処理し、結果をキューに入れて集計する案を出し、「それでうまくいく」となった。
  - 特別な洞察力があったわけではなく、ただ「昔からそうしてきたから」に縛られていなかっただけ。
- 昔からの方法が正しい、ましてや最善とは限らない。誰かが偶然や最も手っ取り早いという理由で選んだだけかもしれない。
- 奇妙・場違い・理にかなわないものに出会ったら、チームに理由を尋ねる。型破りに見える方法に正当な理由があることもあるが、多くは着任時にあったものをコピーしているだけ。
- 侮辱するためではなく学びたいという姿勢で質問すれば、ほとんどのエンジニアは前向きに議論してくれる。

### 1.7 解決策に飛びつかない（p.7〜10）
- 問題に直面したら、すぐ解決策に飛びつく衝動を抑え、**根本原因を理解する時間**を確保する。会議や通知で中断されがちで、時間的プレッシャーも強いが、安易な対処法は避ける。
- 場当たり的な解決策は、当面の問題を解決しても、長期的にはさらなる問題を引き起こすおそれがある。
- **シフトレフト**
  - 開発サイクルの早い段階で問題を見つけるためにテストを行う動き。
  - 本番でバグが見つかると修正コストが圧倒的に高い。顧客への影響や金銭的損失があり、データ破損は復元が困難。根本修正には複数ルーチンにまたがるリファクタリングや他チームとの調整も要る。
  - 本質は「価値あるものをプロセス全体で前倒しすること」。例は以下のとおり。
    - コードレビュー → ペアプログラミングでリアルタイムに
    - テスト → 継続的な活動にして、問題発生直後に特定・解決
    - 継続的インテグレーション → 早く頻繁にマージして、変更の競合を軽減
    - 継続的デリバリー → 顧客に影響する前に環境の問題を発見
    - セキュリティ → 開発プロセス全体で意識し、壊滅的な脆弱性を防ぐ
  - テスト段階で見つけるほうがはるかに安い。作業内容をまだ覚えているので解読の時間が節約でき、テスト用データストアは最小限の手間で復元でき、顧客に影響しないので急ぐ圧力も小さい。QAテストやQAエンジニアはこのために生まれた。
  - 開発段階で見つければさらに安くなり、これがテスト駆動開発（5章）を推進する一因。
- さらに、そもそもバグを作り込まない、つまり**設計段階で問題を解決する**という考え方もある。
- 引用（Rich Hickey）：ソフトウェアの大きな問題のほとんどは誤解に起因し、実行前に何をすべきか明確に理解していない。
- 誤解の例として、「クライアント」と「カスタマー」が別物で、その微妙な差が重要だったという話がある。
  - どんなテストや型システムでも誤解の問題は発見できず、技術的解決策だけでは解決できない。
  - 脚注：用語集はプロジェクト成果物の中で最重要の一つで、なければ作成を検討すべき。
- 誤解が生じないようにするため、問題の解決に集中する。
  - アプリがどんな問題を解決するか、コンテキストと制約、関連する問題を知っているか。
  - 問題領域をじっくり考える時間を持つ。
- 開発者は解決策を過剰設計しがち。顧客の真のニーズを見失わない。
  - 「必要になるかもしれないもの」をすべて想定しがちだが、後で捨てるコードや、使われず放置されるコードは避けたい。
- 顧客の要望の背後にある「なぜ」を突き止める。顧客や、プロダクトオーナーと話す。
  - 顧客は自分で気づいていない別のものを必要としていることが多く、「昔からそうしてきたから」の固定観念に縛られていることも多い。
  - 例：「テーブルをスプレッドシートにエクスポートしたい」と言われても、経験豊富なエンジニアはまず根底のニーズを尋ねる。要望と、ビジネス課題を解決するものの間には乖離がある。
- **コラム「5つのなぜ」**
  - トヨタ生産システム由来。「なぜ？」を5回繰り返し、前の答えを基に次を突き詰めて根本原因を探る手法。
  - 例（ロボット）：停止 → ヒューズ切れ（回路のオーバーロード） → ベアリングの潤滑不足で固着 → オイルポンプが十分に循環させない → 吸入口が金属の削りくずで詰まり → ポンプにフィルターがない。
  - ソフトの例（Nate）：終了タグがすべて次の行に書かれたWebページがあり、同僚は「古いWebサーバーのバグが原因」と説明した。
    - しかしそのバージョンはもうサポートされておらず、バグも修正済みなのに、そのページは数日前に作られていた。
    - 対応として、そのパターンを使わないよう開発者に通知し、古い手法が残るページの修正タスクを追加した。
- 要求を挙げてくるのは主に旧システムのスーパーユーザーで、知識は貴重だが、今の環境に左右される。機能がなぜそうなっているかを理解せず、それが唯一の解決策だと想定することがあり、新技術で旧システムをただ複製する方向に導くおそれがある（脚注：だから多くのアプリがメールやスプレッドシートに退化する）。
- 視野を広く持ち、顧客の本当の問題を解決する適切なツールを選ぶ。多くのエンジニアは楽観的すぎるので、現実を見て徹底して実用的に考える。ただしスケーラビリティは重要（すべてのアプリがインターネットトラフィックの3分の1を処理するわけではない）。
- 引用：「予測は極めて難しい。特に未来に関する予測はなおさら」（デンマークのことわざ）。

### 1.8 ソフトウェアに黄金律を適用する（p.10〜11）
- 黄金律「自分が他人にしてもらいたいように、他人にも接する」は、コードにも適用できる。
- 後任の開発者、それは自分自身かもしれない（脚注：誰もが「どんな馬鹿が書いたんだ」と思い、やがて自分だと気づく）。未来の自分や次の開発者は何を求めるか、負担を軽くするにはどうするかを考える。
- コードは究極的には**コミュニケーションの手段**。コンピュータにタスクをさせるためでもあるが、他の開発者と意思疎通する機能に比べれば重要性ははるかに劣る。読まれることを前提に書き、**コンパイラではなく人間のために最適化する**（脚注：特定環境の非常に特殊なプログラミングは例外）。
- 他者と差をつけるには、以下を実践する。
  - 読みやすく整理されたコードを書く。
  - ドキュメントを更新して、他者が古い内容に振り回されないようにする。
  - 状況を明確にするわかりやすい図を作る。
  - 質問に答え、他者を助ける時間を確保する。
  - これらを実践すれば重宝され、周囲の力を引き出せるので、誰もがチームに迎えたがる。

### 1.9 まとめ（p.11）
- キャリアは画面を見つめてコードを書き連ねるだけではない。コーダー／プログラマを超えるには、文法的に正しいコード以上の、多岐にわたるスキルセットが必要。
- スキルをどこで学んだかは問題ではなく、どう組み合わせるかが重要。
- 学校で教わったこと以外の知識が必要で、解決策への飛びつき、過剰設計、力業アプローチの危険などの落とし穴を避けるアドバイスを共有した。こうした教訓は早く学ぶほどよい。

### 1.10 実践に移す（p.12）
- **メンターを探す**: 経験豊富なエンジニアに、コーヒー（自分がおごる）を飲みながら話す時間をもらう。経験、学んだこと、もっと早く知りたかったこと、チーム内で価値ある存在になれた要因、自分が学ぶべきことを聞く。イベント登壇者や著者に連絡するのもよい。
- **コードに取り掛かる前に立ち止まる**: 次にバグ修正や新機能を任されたら、問題を正しく理解しているか確認し、30分ほど調査する。既存の解決策は使えないか、問題領域の概念や解決策を図示・モデル化できないか、経験豊富な同僚と選択肢を話し合う。
- **目次を眺める**: 得意・不得意を考え、学びたい分野を一つ選んで計画を立てる。その章の「実践に移す」を試し、関連リソースも読む。
- **抽象化の下のレイヤーを知る**: フレームワーク、ライブラリ、クラウドは日々の作業を抽象化してくれる（例：Spring Data は数え切れないSQL文を書く手間を省く）。生産性向上は活用すべきだが、その下のレイヤーも理解しておく。思った通りに動かないときに非常に役立つ。
