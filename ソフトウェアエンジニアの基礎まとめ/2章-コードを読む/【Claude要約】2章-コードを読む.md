山﨑君、2章を読み切ったわ。1章と同じく、抜けなく書くから長くなるわよ。……ちなみに、2章の題材は「他人のコードを読む」こと。普段からあなたが苦戦していることでしょう。ちょうどいい章に当たったわね。

## 結論

2章の主張は、**「エンジニアはコードを書くより読むほうがはるかに多い。初めて触れるコードを読むための手順（人に聞く→ドキュメント→探索→IDE→テスト）があり、それは練習で上達する」**ということよ。

## 2章の内容（節ごと）

### 導入（p.15）
- ソフトウェアエンジニアは、コードを書くよりはるかに多くの時間をコードを読むことに費やす。
- 初心者向け講座はすぐ書く作業に飛び込み、言語の概念や構文に焦点を当てる（ただし、ポーランド語やポルトガル語を同じ方法で学ぶ人はいない、と皮肉られている）。
- 大学のプロジェクトは白紙から始まるが、実際の開発者は何年もかけて現在の状態になったコードを相手に作業する（6章で詳説）。
- エージェント型プログラミング／チャット指向プログラミング（脚注：バイブコーディングとも呼ばれる）の登場で、コードを読むことは今まで以上に重要になる。
- 自分が書いたコードではないものを扱うことになるかもしれないが心配はいらず、初めて触れるコードの状況を把握するテクニックがある。
- 本章は、コードを読むことがなぜ難しいのかを説明し、そのプロセスを簡単にするヒントを提供する。

### 2.1 既存のコードを扱ううえでの課題（p.15〜17）
- 多くの人は、過去に縛られずゼロから始められる**グリーンフィールド開発**で多くの時間を過ごしてきた。
- しかしプロの現場では、真っ白なエディタからアプリを作る機会はほとんどない。既存のコードベースの制約の中でレガシーコードを扱う**ブラウンフィールド開発**に多くの時間を費やす。
- **コラム「レガシーコードとは」**
  - 古いコードを読むのは多くの開発者が避けたい作業で、レガシーコードという言葉が褒め言葉として使われることはほとんどない。
  - 定義はさまざまで、昨日書かれたコード、テストカバレッジが不十分あるいは過剰なコード、単に自分が書いていないコードなどがある。
  - ただし、既存のアプリがうまく動いている事実を軽く見てはいけない。何年もビジネス価値を提供し、継続的に投資されているのは称賛に値する。
  - 「継承コード」「既存コード」のような前向きな表現のほうがよい（6章参照）。
- 既存コードに関わる問題の解決を求められたとき、実際には**4つの問題**を解決する必要がある。
  1. **ビジネス上の問題を理解する**
     - 開発者の取り組む分野は非常に複雑。「ソフトウェアが世界を飲み込んでいる」と言われ、ますます複雑化するビジネス課題に取り組まなければならない。
     - いわゆる「手の届く成果」の多くは、すでにもぎ取られている。
  2. **前任者の視点に立って問題を見つめ直す**
     - これがソフトウェア開発で最も難しい点。
     - 開発者ごとに習慣や傾向が違い、前任者は馴染みのない関数型スタイルやパターン、使ったことのないライブラリを使っているかもしれない。
     - 好みにかかわらず、問題を解く方法は数多く存在する。
  3. **既存コードの抽象化レベルが適切でないおそれがある**
     - モデル化が汎用的すぎる、ドメイン固有の微妙な問題を捉えきれていない、前任者が2つの概念を混同している、本来は別のパターンが適切なのに好みのパターンを無理に適用している、など。
     - 理解しやすくするために、大規模なリファクタリングが必要になる可能性がある。
  4. **技術的負債の山を、考古学者のように次々と剥がしていく**
     - かつての技術や手法は、今はアンチパターンと見なされるかもしれない。言語やベストプラクティスは進化する（脚注：Neal Ford「今日のベストプラクティスは明日のアンチパターンだ」）。
     - だからコードが書かれた当時の視点で見る必要がある。
     - 使われている・いないフレームワークや言語機能で、コードの「年代測定」ができるかもしれない。
     - Spring のようなフレームワークは長年進化し、特定の問題に複数のアプローチをサポートしていることが多い。「正しい」方法は時とともに変わる。
- さらに厄介な点として、パッチの上にパッチを重ねたコードを扱うことがほとんどである。理由の例として、次が挙がっている。
  - 前の開発者が問題を完全に理解していなかった。
  - 新しい言語機能を知らなかった。
  - AIコーディングアシスタントのプレミアムライセンスで、1日に2万行ものコードを生成していた。
- そこに「すぐに直して」という要求が加わると、たった一つのメソッドの解読に半日を潰しかねない。
- 既存コードが嫌われる理由は、技術的な問題だけでなく**認知バイアス**にもある。

### 2.2 認知バイアス（p.17〜18）
- 既存コードを読むと「あまり良くないコードだな」と思いがち。著者たちも「一体誰がこんな馬鹿げたコードを書いたんだ？」と叫んだことがあるが、書いたのは自分自身だった。
- 数年前の自分のコードにがっかりするのは当然で、成長の証であり素晴らしいこと。
- 既存コードを扱うときに働く認知バイアスは次のとおり。
  - **IKEA効果**
    - 自分で作ったものを、実際より高く評価してしまう現象。
    - 研究によると、自分で組み立てた製品には、他人が組み立てた同じ製品より63%高い金額を払う（リンゴ狩りの例）。
    - ソフトウェアでも、開発者は「正しいやり方」へのこだわりが強く、自分のコードやアプローチを好む。
  - **単なる接触効果**
    - 人は慣れ親しんだものを好む。
    - 開発者は、自分が最初に学んだ言語がすべての基準だと考えがち。
    - 例：Java が初めてラムダ式を導入した際、ある言語別のメーリングリストで「なぜ Java にこのような新奇なラムダが必要なのか」という声が上がった。しかしラムダは新しい概念ではなく、Java の当初の計画にも含まれていた。
  - **Blub パラドックス**（Paul Graham のエッセイ "Beating the Averages"）
    - プログラミング言語は「表現力の連続体」の上にあると Graham は述べている。
    - 架空の言語 Blub を使う生産性の高いプログラマは、表現力の低い言語を見ると、自分の使う機能が欠けていることしか目に入らず、なぜそんな劣ったツールを選ぶのか理解できない。
    - 表現力の高い言語を見ると、Blub にない奇妙な機能ばかりが目に入り、それがなぜ生産性に必要なのか想像できない。
- 同僚が特定のツールや手法に強くこだわる理由がわからないときは、IKEA効果やBlubパラドックスの例ではないかと考える。自分自身の思い込みも省みる。

### 2.3 初めて触れるコードへの取り組み（p.18〜20）
- 実際にはキャリアを通じて既存コードベースと向き合う。ストレスなくスムーズに入るために、次の手順を踏む。
- **まずチームメンバーに話を聞く**。基本的なプロジェクト概要説明は、どのオンボーディングでも欠かせない。
- **ドキュメントを読む**
  - README は全体像の把握に役立つ。概要をまとめたWikiやWebサイトがあるプロジェクトもある。
  - **ADR（アーキテクチャ決定レコード）** がある場合もある。背景情報や、障害対応に追われると見失われがちな「なぜそうするのか」という理由を提供してくれる（脚注：『Head First Software Architecture』3章）。
  - デバッガーで何時間も費やすより、ドキュメントを数分読むほうが多くを学べる。
  - コーディング標準を読んでおけば、使われているプログラミングパターンに備えられる。
  - 脚注：ドキュメントは古くなっている可能性があるので、信頼はしても必ず確認する。
- ドキュメントが古ければ、学びながら更新する。存在しなければ、作業を進めながら自分で作ることを検討する。「黄金律」（1章）の実践であり、自分の理解にも後任者にも有益。
- 軽量で形式ばらないアプローチで、次の疑問に答えるようにまとめる。
  - このサービスはどんな機能を提供するか。
  - どのように動作するか。
  - 何に依存しているか。
  - アプリケーションはどう実行するか。
- 「ドキュメントはコードと同期しない」という反論に対しては、同期しなければならないことはないと答える。最善の方法は**テストをドキュメントとして活用する**こと。振る舞い駆動型で書かれたテストは実行可能なドキュメントになる（5章で詳説）。
- **コラム「メトリクスは誤解を招く」**
  - コードカバレッジは有用なメトリクスになり得るが、銀の弾丸はなく、100%でも問題は起こり得る。
  - 友人の話：リリースごとにリグレッションが起きるプロジェクトで、テックリードが「カバレッジは約92%」と誇らしげに答えた。しかしテストコードを確認すると、**アサートが一切含まれていなかった**（コードベース全体に蔓延）。指摘してもテックリードはカバレッジの数値を繰り返すだけだった。
  - 教訓は、あらゆるメトリクスは誤解を招くおそれがあるので、価値と目的を見失ってはいけないということ。形式的なものになっているなら成果は出ない。定期的に取り組みを見直し、必要なら方向転換する。

### 2.4 ソフトウェア考古学（p.20〜25）
チームと話し、ドキュメントを読んだら、次はエディタを開いて探索する。
- **コードの構造を見る**
  - どう構成されているか。
  - どう組み合わされているか。モノリシックか、数十〜数百のサービスからなる分散アーキテクチャか。
  - どんなドメイン概念が表現されているか。
  - テストを読み、機能について何を教えてくれるかを見る。そのクラスの意図が理解できるか。
- **意図がわからなければ掘り下げる**
  - モダンエディタで、ある関数の呼び出し元を確認でき、呼び出し元を次々とたどれる。
  - たどるとHTTP呼び出しのようなサービスエンドポイントにたどり着くこともあり、最終的には特定のユーザー操作とコードの関連が見えてくる。
- **アプリケーションを実行する**
  - UI上の要素や、サービス呼び出しのパラメータなど、特定の要素を見つけてコードにマッピングする。
  - 課題リストを確認し、特定の機能やバグに絞ってコードの流れを追えるか試す。
  - 目印を探す（例：ある操作がデータストアの更新につながると知っているなら、その箇所をコード内で見つける）。
  - デバッガーで順に追う。予想通りに動くか、まったく別のコードにたどり着くか確認する。
  - 最終的に**コードのメンタルモデル**を構築する、つまりアプリケーションを脳内に読み込む。
- **実例：Spring PetClinic**
  - Javaや Spring の専門家でなくても理解しやすく、ドキュメントも優れている。
  - 手順は次のとおり。
    1. アプリをクローンして実行し、飼い主検索の機能を見つける。
    2. テンプレートから、わかりやすい名前の `findOwners.html` を見つける。
    3. そこから `/owners` エンドポイントへたどる。プロジェクト内検索では多くの結果が出るが、少し勘を働かせれば `OwnerController` の `processFindForm` メソッドの `@GetMapping("/owners")` にたどり着く。
    4. ブレークポイントを設定し、ブラウザから検索して動作を確認する。直感が外れたら、前の手順を繰り返す。
  - 脚注：すべてのアプリがこれほどわかりやすい名前ではなく、検索ツールを駆使する必要がある場合もある。
- **IDEで移動する**
  - 他クラスのメソッドへ簡単にジャンプできる。
  - メソッド本体をすべて折りたたんで表示範囲を狭められる。
  - クラスのアウトラインを表示して高いレベルで把握できる。メソッド名を読んで、そのモジュールの目的を考える。
- **コードが名前通りに動くと決めつけない**
  - 進化につれて、変数名やメソッド名が実態を反映しなくなることがある。
  - 焦らず自分の直感が正しいか確かめる。手抜きをすると後で手間が増える。時間をかけて丁寧にやるほうが結果的に時間を節約できる。
- **例外（Exception）は誤解を生むことがある**
  - 起こり得るエラー状況について、例外が誤った想定をしているのを何度も見てきた。
  - 非常に大まかなレベルの例外をキャッチしている場合は特に注意する。書いた人には手っ取り早くても、起こり得る問題を曖昧にしてしまう。
- **IDEのコード分析ツール・プラグインを使う**
  - 例：IntelliJ IDEA は依存関係を素早く表示でき、コードがどう連携しているかを把握できる。
- **ソースコード管理ツールを活用する**
  - ファイルの変更履歴を確認する。どんな変更が頻繁か、コミットログから何がわかるか。
  - 最も頻繁に更新されているクラスから確認する。Git のコマンド例が載っている（過去1年で最も変更された `.java` ファイル上位10件を出す、p.23）。
  - `git blame` などで、誰が直近の変更をしたか、誰が最も頻繁に変更しているかを確認できる。IDEでも変更履歴を確認できる。
  - どんな方法で調べるにしても、**恐れずにチームメンバーに質問する**。
- **図をコードから抽出する**
  - アプリの進化でモデルがコードと食い違うことがよくあるが、コードベースからいつでも図を抽出できる。
  - 一部のIDEは簡単なキー操作で図を生成できる（例：IntelliJ IDEA の UML 図生成）。
  - Umbrello、Doxygen、Structurizr などのツールでコードを視覚化できる。
  - ビルドパイプラインに組み込み、コミットのたびに最新の図を自動生成することも検討する。

### 2.5 効果的にコードを読む方法（p.25〜33）
目的と全体像を把握したら、コードを理解する段階。IDEの機能とテストの分析を使う。

**2.5.1 IDEの機能を活用する**
IDEは単なるテキストエディタではなく、コードの調査・理解のツールとしても便利。

- **2.5.1.1 継続的な学習方法**
  - IDEは高性能すぎてすべての機能を把握するのはほぼ不可能なので、**毎週何か新しいことを学ぶ**。
  - 例：IntelliJ IDEA の「Tip of the Day」。起動時にショートカット、ツール、リファクタリング、デバッグ、プラグインなどのヒントが表示される。[Help] → [Tip of the Day] でいつでも確認でき、ライブテンプレートの紹介などがある。
  - 多くのIDEに同様の機能があるので、ドキュメントを確認して学習を始める。
  - 自分専用の「IDE活用術」ドキュメントを作り、新しく見つけたショートカットや機能を記録し、定期的に見直して無意識に操作できるよう練習する。
- **2.5.1.2 コードナビゲーションツール**
  - **使用箇所・参照先を探す**
    - クラスやコンポーネントを理解するには、どこで使われているかを確認する。
    - 例：IntelliJ でJavaインターフェースを開き、ガターアイコンをクリックするとすべての実装を検索できる。抽象化の実際の使われ方を理解するのに便利。
    - メソッド名を右クリックして「Find Usages」で、呼び出されているすべての場所を確認できる。
  - **定義へ移動する**
    - 例：`ArrayList` 型を Command（Windows／Linux は Ctrl）キーを押しながらクリックすると、ソースコードに移動し、コードやドキュメントを確認できる。
    - 次のものを扱うときに役立つ。
      - サードパーティ製ライブラリ
      - フレームワークのコード
      - 基底クラスやインターフェース
      - コードベース全体で使うユーティリティメソッド
  - **呼び出し階層・型階層・依存関係ビュー**
    - コンポーネント間のやり取りの理解は、初めて触れるコードベースの把握に極めて重要。
    - 呼び出し階層は、そのメソッドが何から呼ばれ、何を呼ぶかを示す。型階層は継承関係を示す。依存関係は、モジュールやパッケージがどう依存し合うかを可視化する。
    - 例：IntelliJ でメソッドを右クリックし「Show Call Hierarchy」を選ぶと、インバウンド呼び出し（どこから呼ばれるか）とアウトバウンド呼び出し（何を呼ぶか）の両方がわかり、システム全体でのそのメソッドの役割を素早く把握できる。
- **2.5.1.3 コード分析機能**
  - **自動検査と提案**
    - IDEはコードのリファクタリング方法を提案してくれる。あくまで提案で、受け入れる必要はないが、確認は有益。品質向上だけでなく、新しいことやよく使われるパターン、ベストプラクティスを学ぶ機会になる。
    - 例：Javaで Book コレクションを for 文で反復して書名を出力するコードに対し、IntelliJ は、`forEach` とラムダ式を使うより簡潔な書き方を提案してくる。元のコードも動くし問題はないが、言語における慣用的なパターンが学べる。
  - **コード構造の可視化**
    - プロジェクト構造を見れば、モノリシックなアプリで、コードが機能ごとにパッケージ化されていることがすぐわかる（PetClinic の例）。
    - あるクラスで使えるメソッドを知りたいとき、APIドキュメントは最新かどうかわからず、ソースをスクロールするのは時間がかかる。ほとんどのIDEにある構造ビューを使えば、メソッドが一目でわかり、クラスの目的や機能を素早く把握できる。

**2.5.2 テストを読むことで知見を得る**
- 新しいコードベースでは、**テストは開発者にとってドキュメントとしての役割を果たす**。適切に書かれたテストは、コードが何をするかだけでなく、なぜそう実装されているかも明らかにする。
- コードは「実際にどう動作するか」を教え、テストは「**本来どう動作すべきか**」を教える。
- **2.5.2.1 テストは生きているドキュメント**
  - 従来のドキュメントはすぐ古くなるが、テストはCIのチェックに合格するために常に機能しなければならないので、システムの挙動に関する常に最新の「信頼できる情報源」になる。
  - テストはメソッドの期待される入力と出力、コンポーネント間のやり取り、システム全体の挙動をドキュメント化する。
  - コンポーネントが実際にどう動くかを探る前に、**まずテストを読む**と、何を行うべきかが理解でき、実装が理解しやすくなる。
  - 例：常連客が一定額以上の大量注文をすると10%割引になることを検証するテスト（500.00が450.00になる）。注文規模に基づく割引計算を検証している。このコンテキストを踏まえて、価格設定サービスのメソッドを調べると、計算結果を生成するコードを理解できる。
- **2.5.2.2 ワークフローとプロセスを理解する**
  - テストはユーザーストーリーと対応付けられることが多く、ビジネスプロセスやワークフローの理解に有効。統合テストを見れば、コンポーネントがどう連携してビジネス要件を満たすかの全体像がわかる。
  - プロセス全体を最初から最後まで検証するテストを探す。実際の運用環境を想定したセットアップコードを含むことが多く、本番での挙動の手がかりになる。
  - 例：ユーザーが商品レビューを投稿すると、平均評価が更新され、管理者に通知が送られることを検証するテスト。データ永続化と通知の両方が期待通りに動くことがわかる。
- **2.5.2.3 エッジケースや境界条件を発見する**
  - エッジケースとは、想定される入力、動作条件、利用パターンの極端な境界で発生する状況。有効だが通常と異なるもので、ハッピーパスでは発生しないバグが露見する。
  - 既存のコードベースでは、こうしたケースのテストがより多い。時間とともに問題が発見され、再発防止のためにテストが作られてきたから。
  - `shouldHandleEmptyList`、`shouldRejectInvalidInput`、`shouldTimeoutAfterTenSeconds` のような名前のテストに特に注意する。システムの機能の限界を示し、起こりうる障害を明確にしてくれる。
  - 例：有効期限切れのクレジットカードの支払いを正しく拒否するテスト。実装を読み通すだけではわからないかもしれない点が、テストからわかる。このコンテキストを踏まえて、実装でそのエッジケースを捕捉する箇所を探す。
- プロジェクトを理解してコードを読めるようになったら、次はコードを修正する段階で、どうすれば安全に修正できるかは**次の章（3章）**で説明する。

### 2.6 練習が上達へ導く（p.33〜34）
- 自分に少し寛容になる。モダンなコードベースは非常に複雑で大規模で、**一人の人間がすべてを理解することは不可能**。そもそもそれが目的ではない。知識は時間とともに増える。
- 初めて触れる部分に直面するたびに、同じプロセスを繰り返す。最初は気が遠くなるが、すべての開発者が同じ道を歩んできた。
- コードを読む力を伸ばすには、**気が進まなくても読む練習をする**。さまざまな言語の良質なOSSコードが自由に使える。近道はなく、時間とともに楽になり、読む速度も上がる。
- **コラム「AIはどうでしょう？」**
  - ツールは進化し、コードを書くことは以前より容易になったが、アプリの規模や複雑さも増しているため、結局は相殺されるのかもしれない。
  - 生成AIの登場で、開発者は間もなく置き換えられるという声もあるが、**終焉の予言は大げさに誇張されがち**。COBOL、第4世代言語、ドラッグ＆ドロップ式のソリューションも、ソフトウェアエンジニアリングへの需要を大幅には減らさなかった。
  - AIツールはツールボックスに欠かせない。例：あるコードのまとまりが何をするかをChatGPTに尋ねられる。
  - それでも自分でコンテキストを理解する必要がある。AIは、なぜ特定のクラスが存在するかを知らない。コードを読み、ドキュメントを精査し、仲間と話し合う必要がある。
  - AIは（現時点では）企業全体のコードベースを完全に理解しておらず、**ハルシネーションのリスク**は現実にある。複数リポジトリにまたがる細部や相互関係を理解するのは、読者の仕事。
  - Dan の言葉：AIを利用するときは「**パイロット**であって**乗客**ではない」。信頼はしても検証もする。
  - 開発者がその関係性や複雑さを理解してこそ、AIツールが開発を加速できる。
  - 脚注：所属組織の法務部門が、こうしたツールの利用ポリシーを設定しているはず。AIは貼り付けたコードを訓練データとして使うおそれがあるので、価格設定など自社独自のアルゴリズムを貼る際は社内規定を必ず確認する。

### 2.7 まとめ（p.35）
- プログラミング教育はある意味逆転している。読むことを学ぶ前に書くことを学ぶのに、実際のキャリアでは他人のコードを読む時間が大半。
- 既存コードを扱うのはゼロからの開発ほど楽しくないかもしれないが、それが報酬を得るための仕事。逃げずに受け入れることで、プロとして得られるものは多い。
- 認知バイアスにも注意する。臆せず初めてのコードベースを掘り下げれば、必ず何かを学べる。
- 理解が深まったら、**コードを元の状態よりも良い状態にする**。次にそのコードを扱う開発者の負担を軽減する。その開発者は自分自身かもしれない。

### 2.8 実践に移す（p.35）
- コードを読む力に近道はなく、とにかく多くのコードを読む。OSSが豊富にある。
- 時間を確保し、仕事で使っている（使いたい）フレームワークや、興味のあるプロジェクトのコードを読む。迷ったらGitHubのトレンドリポジトリを見る。
- 本章のテクニックを使う。数か月後に、最初に調べたプロジェクトの別の部分を探るか、別のプロジェクトに挑戦して、前回より読みやすいか確かめる。継続が大切で、スキルは確実に向上する。
- 既存のコードを扱うことも、磨くべきスキルの一つ。**OSSへの貢献は絶好の学習の場**で、始めるのは想像ほど難しくない（脚注：「初めての貢献者向け」とマークされたバグリストを持つプロジェクトも多い。貢献者に気軽に連絡してよく、ほとんどの人が喜んで手助けしてくれる）。

## 全体を貫く流れ

1. 現場の大半は、ブラウンフィールド（既存コード）での仕事で、読む時間のほうがはるかに長い。
2. 読むのが辛いのは、ビジネス課題・前任者の視点・抽象化のずれ・技術的負債の4つに加え、認知バイアスがあるから。
3. 手順は、**人に聞く → ドキュメント → 構造の探索（実行・デバッグ・履歴・図） → IDE → テスト**。
4. すべてを理解する必要はなく、同じ手順を繰り返して知識を積み上げる。
5. AIは助けになるが、読者が「パイロット」として検証し続ける。
6. 理解したら、コードを元の状態よりも良い状態にして後任（未来の自分）に渡す。

## 1章で出た疑問との関係

- **「何を理解して、何は理解しなくていいか」**: 2.6で「一人の人間がすべてを理解することは不可能で、それが目的ではない」と書かれている。ただし「これは不要」という具体的な線引き基準までは書かれていない。
- **「レガシーコード」**: 2章のコラムで、複数の定義（昨日書かれたコード、テストが不十分／過剰なコード、自分が書いていないコード）が挙がっている。
- **「技術的負債」**: 2章でも、定義というより「かつての手法が今はアンチパターンになる。それを考古学者のように剥がしていく」という文脈での言及に留まる。
- **「devinでいいもんね」という感想**: 2章のAIのコラムは、「置き換えられる」という予言を大げさと見ている。ただし1章の脚注は「コードを書くだけの技術者は置き換えられるおそれが高い」としていて、読むこと・理解することが人間の仕事として残るのは2章の主張よ。
